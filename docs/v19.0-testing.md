# Django 19.0 testing

## Status

The Trixie appliance builds and reaches normal multi-user operation in the
Docker rootfs harness. The Django-specific acceptance verdict is pending a
shared harness correction. The current harness exits on a nonzero
`docker exec` result before copying the child result file, so the failing
assertion is not retained.

A disposable Trixie rootfs separately passed the application assertions for
the sample site, static asset, bundled documentation, administrator login,
Apache mod_wsgi, Django ORM access to MariaDB, root database access, IPython,
Webmin package integration, and the Debian updater channel. This fixture is
supporting diagnostic evidence, not a substitute for the pending appliance
acceptance run.

## Dependency source decision

All application dependencies come from Debian Trixie. No upstream archive or
additional updater is required.

| Component | Debian package | Version observed in Trixie |
| --- | --- | --- |
| Django and its documentation | `python3-django`, `python-django-doc` | `3:4.2.28-0+deb13u2` |
| Apache WSGI integration | `libapache2-mod-wsgi-py3` | `5.0.2-1` |
| Django MariaDB driver | `python3-mysqldb` | `1.4.6-2+b5` |
| Enhanced shell | `ipython3` | `8.35.0-1` |
| Database service | TurnKey MySQL plan on Debian MariaDB | `11.8.6` |

The supported update path is Debian APT. The non-destructive updater check is:

```sh
apt-get update
apt-cache policy python3-django
```

In the disposable Trixie fixture, signed metadata refreshed successfully,
`python3-django` had an eligible candidate from `trixie/main`, the security
index was present at `trixie-security/main`, and the installed package version
was unchanged by the check.

## Inherited Core 19 evidence

testing does not exercise the installer, appliance kernel, or hardware. A
separate ISO boot is unnecessary for Django once the Core or TKLDev ISO path is
proven for v19.
